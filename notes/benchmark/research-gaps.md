# AIOps Benchmark 研究缺口

本清单综合六篇论文。每项均区分领域研究问题与本地证据缺口；用户提出的挑战赛风险尚未凭本地样本核验。

## 跨论文研究问题

1. **Ground Truth 的边界和不确定性：** 注入目标、首个受影响节点、首个业务症状、根因组件、传播节点与恢复时间通常不同。如何统一记录多根因、Unknown、竞争解释、区间时间与证据来源？
2. **故障影响的真实性：** RCABench 用 SLI 验证有效注入，但业务影响门槛如何跨业务定义？如何保留未影响注入作为分母，避免只发布“好诊断”的样本形成选择偏差？
3. **分组泛化和 Shortcut：** 节点角色、注入模板、时间窗、日志模板、CLI 输出、候选集都可能成为标签代理。怎样形成跨实体/故障族/拓扑/时间的泄漏审计，并保证测试集仍有足够类别覆盖？
4. **传播标签语义：** 根因—传播—症状—业务影响链在 RCABench、AgenticOpsEval、CTBench 中分别是层级、因果步骤或运维路径。哪些边来自实际证据，哪些是专家推断？怎样让不同数据集间可比？
5. **Agent 过程指标构念效度：** NIKA 的真实工具调用、AgenticOpsEval 的 evidence coverage、CTBench 的 exact golden action route 各自测什么？如何容纳等价观测并核对证据是否被正确使用，而不把“读过证据”当“由证据推出结论”？
6. **统一质量—成本—安全报告：** 传统 AD 的延迟、Agent 的 Token/工具数、路径覆盖和修复风险如何分开报告？能否给相同任务预算和可见信息，而不把不同过程指标压成单一总分？
7. **标注质量与外部效度：** 历史企业数据、故障注入测试床、网络仿真、交易记录合成和 CLI replay 代表性不同。怎样在论文中量化选择、剔除和专家分歧，并在第二种环境验证迁移？
8. **版本化可复现：** 论文、公开数据 release、项目 main 与 scorer 可能不同步。如何为每个结果冻结数据 hash、标签版本、代码 commit、工具接口、预算和模型版本？

## 本地挑战赛待补证据

- 原始样本、数据字典、单位、采样率和事件级独立样本数。
- 数据时间跨度、拓扑和节点角色、数据来源与许可。
- 故障生成/注入脚本、实际命中记录、用户影响/恢复证据。
- 故障类别、起止时间与根因标注规则及复核记录。
- 用户提出的 inode、process count、fd 等特征生成机制和正常对照。
- 类别长尾、角色关联、故障传播范围、多模态对齐的实际统计。
- 训练/测试切分、现有 AD/RCA 基线及指标实现、公开仓库版本。
- Agent 可见数据、工具、权限、Token/时间/调用预算及安全设置。

因此目前不能断言这些字段存在数据泄漏、标签不准、绑定偏差或任何已验证的创新差异。

## 可检验问题

1. 独立事件组切分、按故障族/模板/实体/拓扑/时间留出后，结果与随机切分差多少？
2. 仅用时间戳、节点角色、inode/process count/fd、单指标或脚本元数据可达到何种基线？消融/错配测试分别改变什么？
3. 注入、最早异常、业务影响、告警、缓解和恢复时间能否被不同观测独立定位？标注分歧有多大？
4. 拓扑、多模态和传播证据是否提升跨实体泛化，而非记忆 ID？
5. Agent 正确答案的证据是否真实支持结论？不同调查路径如何公平处理？
6. 原始数据、生成器、标签、split 与 scorer 能否在许可范围内公开并由第三方复现？

优先级建议：先补齐本地数据谱系和评估版本，再针对 1–4 设计廉价 Shortcut 与边界验证；在此之前不立足于未经证据支持的投稿创新点。

## 独立阅读反馈新增问题

- 对同一事故并行应用 SLI、根因直接观测、专家可追溯三种门禁，哪些长距离、弱症状或部分故障发生了分布改变？
- 固定答案和任务，仅改工具返回的直接/间接观测，再测试可替代证据路径。能否在覆盖、正确性和取证成本保持分母可比？
- 固定模型和可见工具，以任务配对比较 Harness 的状态复用、异常恢复和提交抽取。哪些差异在控制预算及多重比较后仍成立？
