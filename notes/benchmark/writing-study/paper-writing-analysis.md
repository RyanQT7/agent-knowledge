# Benchmark 论文的叙事、组织与图表写作分析

## 范围与证据口径

本分析复用七篇论文的精读笔记，并对本地 PDF 作了写作视角的定向核对：标题页/摘要、引言与贡献列表、章节边界、关键结果页和代表性图表。重点论文为 RCABench、NIKA、CTBench、NetArena；OpenRCA、AgenticOpsEval 和 *Constructing Large-Scale Real-World Benchmark Datasets for AIOps* 用于补充数据谱系和验证方式。

页数分配是按本地 PDF 的主体页、附录和参考文献粗略估算，受版式、双栏、图表密度影响，不是字数统计。重要定位优先使用论文的章节、表图和附录。RCABench 本地 PDF 是 arXiv v2，精读笔记另核对 FSE 2026 正式版；下文如无版本说明，采用本地 PDF 对应定位，并以笔记所载正式版交叉校正。没有重新精读全文、执行基准或审计本地挑战赛数据。

## 1. 标题、摘要与引言如何建立论文主张

| 论文 | 标题传递的研究定位 | 摘要与引言的叙事推进 | 代表性原文短语及其作用 |
|---|---|---|---|
| [RCABench](../../../papers/benchmark/rcabench/notes.md) | *Rethinking the Evaluation…* 把问题放在“评价是否可信”，而非单纯宣布新数据集。 | 先指出 RCA 重要，再用 SimpleRCA 在四个旧基准上的表现提出反常现象；继而系统审计故障注入、调用图和信号模式，介绍生成与 SLI 筛选方法，最后报告 11 个方法在新数据上的退化与失效模式。 | 摘要中的 “overestimation of the performance” 将低估 Benchmark 难度与高估算法能力连接起来。它使后文的旧基准审计成为论文论证起点，而非相关工作背景。定位：Abstract、§1、§3.2。 |
| [NIKA](../../../papers/benchmark/nika/notes.md) | *A Network Arena for Benchmarking AI Agents on Network Troubleshooting* 直说对象、评价对象和任务域，突出环境/平台贡献。 | 从网络排障需要跨设备、跨层调查，转向静态或难复现基准不能观测工具交互的缺口；然后给出场景—故障—流量—目标任务模型、AAL 与执行记录，最后用三种模型和 150 个任务说明诊断难度及效率代价。 | 标题中的 “AI Agents on Network Troubleshooting” 明确将贡献锚定在可交互 Agent 评价，不把它包装成新的网络诊断算法。定位：Title、§1–3。 |
| [CTBench](../../../papers/benchmark/ctbench/notes.md) | *Evaluating Troubleshooting Capabilities…in Realistic Telecom Network Operations* 把“能力评价”与运维场景放在前面。 | 从真实 NetO&M 的部分可观测、多厂商、序列决策需求引出基准缺口；对比现有网络基准；提出 RCA 和路径恢复任务、专家证据轨迹及元数据；最后以 Agent 结果显示答案正确与证据充分并不等价。 | 摘要称 Agent “frequently fail to gather the requisite diagnostic evidence”，先给读者一个可验证的过程评价主张，再由 Table 18 的正确答案子集支持。定位：Abstract、§1、§5.1、Appendix C.1。 |
| [NetArena](../../../papers/benchmark/netarena/notes.md) | *Dynamic Benchmarks…in Network Automation* 以动态生成和广义自动化定位，范围比 RCA 更宽。 | 引言把静态小样本、污染风险、统计不确定性和动态任务 GT 难生成串成问题；§3提出状态—动作执行抽象；§4用三项实验验证样本规模、难度分解与 SFT 泛化；结尾讨论 RL 和对抗采样用途。 | 摘要的 “correctness, safety, and latency” 概括多维执行评价；三项指标分开展示，后文也呈现三者之间的取舍。定位：Abstract、§1、§3.3–4。 |
| [OpenRCA](../../../papers/benchmark/openrca/notes.md) | 问句式标题 *Can Large Language Models Locate…?* 将论文写成能力检验，而不是声称已经实现自动 RCA。 | 先提出企业遥测、长时间窗和多字段根因定位的难题；接着描述数据筛选、任务形式和 RCA-Agent；再比较采样方法、模型和系统；案例及讨论用于解释低分、CoT 与多轮查询差异。 | 标题中的 “Can…Locate” 保留经验问题的开放性。实验回答的是经校准数据与设定输入条件下的能力，不是任意生产环境能力。定位：Title、§1–6。 |
| [AgenticOpsEval](../../../papers/benchmark/agenticopseval/notes.md) | *A Multi-Dataset Benchmark…* 把多数据集和 Agent 评价作为主贡献。 | 从 outcome-only 指标不能区分碰巧答对与证据支撑，引出 Localization/Identification/Reason 三支柱；AIOps2025 与 RCA100 分别提供轻量 key evidence 和更深 causal checkpoints；Discussion 转向质量、复用和限制。 | “reasoning-process evaluation paradigm” 将新增贡献压缩为评价构念，而不是以参赛队伍数替代科学贡献。定位：Abstract、§1、§3–6。 |
| [Constructing Large-Scale](../../../papers/benchmark/constructing-aiops-benchmark/notes.md) | 描述性标题强调建设过程、规模和真实来源，适合数据集/资源论文。 | §1–2 先定义 AIOps 问题和本工作；§3–5 分别介绍 KPI 异常、结构化多维 RCA、故障发现/诊断三条数据谱系；竞赛历史和公开评测支撑可用性；§6 总结。 | “three large-scale, real-world benchmark datasets” 在摘要中直接列出交付物，随后分章节逐一界定其任务和来源。写作上也提示三套数据不能合成一个无差别规模数字。定位：Abstract、§2–6。 |

### 1.1 引言中的“已有工作不足”如何变成证据

较有说服力的叙事不会只写“现有数据集有限”，而会把不足变成可检验的对照：

- **RCABench** 先用 SimpleRCA 检验旧基准是否可被简单症状规则解决，再解释故障与可观测信号的结构原因。问题证据在方法设计之前出现，降低“先造数据再宣称更难”的循环论证风险。（§3.1–3.2，Table 2、Fig. 2）
- **CTBench** 用 Table 1 明示任务、部分可观测、异构设备和专家证据四个差异，再用 Figure 1 展示候选任务如何盲审、协商和保留。前者说明“相对已有工作多了什么”，后者说明“数据如何达到可用质量”。（§2.2，Table 1、Fig. 1）
- **NetArena** 先把污染、样本数小导致 CI 重叠、静态最终答案评价等问题分开，再用大样本动态 query 和交互状态转移逐项响应。该论证需要同时承认随机生成任务是否独立仍需验证。（§1、§3、§4.1，Fig. 3）
- **NIKA** 用具体交互案例证明只报告最终答案会隐藏调查过程，但其主要贡献仍是可复现运行环境、工具接口和轨迹记录；若要证明某类设计导致性能变化，需要额外的控制实验，不能只凭轨迹示例归因。（§3.3、§4.2，Figs. 3–6）

### 1.2 工程产物与科研贡献的写作边界

数据、工具、任务和代码“做出来了”是资源贡献；科研论证还要说明它们让哪些研究问题变得可测，产生了什么可复核发现。

- **基准有效性问题**：RCABench 用 SimpleRCA 审计和新集上的失效分析支撑；OpenRCA 以多个系统、任务字段难度和 Agent/采样对照支撑。
- **交互环境问题**：NIKA 用真实可执行仿真任务、工具轨迹、检测/定位/RCA 结果及拓扑规模实验支撑；NetArena 用状态转换抽象与样本量/复杂度/SFT 实验支撑。
- **过程评价问题**：CTBench 用专家 golden actions、正确答案子集的证据缺失统计及 O2→O1 消融支撑；AgenticOpsEval 主要展示标签与计分设计，并未提供完整多模型受控比较，论文不应被描述成已经证明新评分能提高 Agent 能力。
- **数据资源价值**：ZTE 文章用长期公开使用及多届竞赛说明可用性；竞赛参与规模不能单独证明标签准确、统计显著或跨数据集泛化。

## 2. 篇章组织与大致篇幅

下表的“主体”指论文论证部分粗略页数，不计精确字数；双栏图表会显著影响每页信息量。

| 论文 | 主体结构与篇幅（约） | 附录/补充材料承担的任务 | 组织选择的写作作用 |
|---|---|---|---|
| RCABench | 本地 arXiv PDF 主体约 17–18 页：引言/相关工作约 17%；旧基准预研究约 22%；Dataset Construction 约 17%；Study Design 与 Results 约 33%；讨论/结论约 11%。（§1–8，按页粗估） | 主要结果与细节分布在长结果部分及版本材料；正式版和 arXiv v2 的定位需按版本区分。 | 将“旧基准为什么有问题”先证明，再给出自己的构造，最后验证难度，形成问题—构造—验证的闭环。 |
| NIKA | 主体约 11 页：引言/背景约 27%；NIKA 框架约 36%；实验约 27%；讨论/结论约 9%。（§1–7，按页粗估） | Appendix A 列 incident pool 与网络场景；Appendix B 列运行时、MCP tools 与提示词。 | 正文保持系统主线紧凑，附录承担任务可复现、工具接口和提示细节。 |
| CTBench | 主体约 10–11 页：引言/相关工作约 27%；任务与构造约 32%；指标协议和实验约 32%；讨论/结论约 9%。（§1–7，按页粗估） | Appendix A 任务与标注；B 补充指标；C 补充实验；D 统计与复现；E 轨迹失败分析；F 能力讨论。附录占本地 32 页 PDF 的大部分。 | 主文快速说明贡献与主结果，附录承载足以复核指标、标注、误差和运行设置的证据，避免主文塞满公式和任务样本。 |
| NetArena | 主体约 10 页：引言/相关工作约 30%；统一方法约 20%；三组实验约 30%；用途和讨论约 20%。（§1–5，按页粗估） | Appendix B–D 按 Capacity Planning、Routing、K8s 分别说明环境、生成、Agent 使用和指标；正文依赖附录复现实例。 | 先给跨应用抽象，再将实现细节按任务分栏，适合框架型 Benchmark；抽象边界需要被各应用真实实现和实验覆盖。 |
| OpenRCA | 主体约 10 页：问题、数据和任务约 40%；RCA-Agent 与实验约 40%；案例、相关工作和讨论约 20%。（§1–8，按页粗估） | Appendix A 数据和校准；后续附录给任务合成、Agent prompts、采样与案例、补充分析。 | 将数据建设与基线方法并列：资源贡献回答“可测什么”，Agent/采样结果回答“模型目前能做什么”。 |
| AgenticOpsEval | 主体约 9 页：引言/相关工作约 22%；设计原则约 22%；AIOps2025 与 RCA100 各约 22%；讨论/局限/结论约 11%。（§1–7，按页粗估，章节跨页） | arXiv v1 无独立附录；需在短篇幅内压缩协议与数据细节。 | 两套数据集对齐三个评价支柱，但不同数据深度不可直接混为同质排行榜。 |
| Constructing Large-Scale | 期刊正文约 8–9 页：引言/概览约 20%；Dataset A/B/C 分别约 20%/25%/30%；总结约 5%。（§1–6，按页粗估） | 没有大型形式附录；关键过程嵌在 Dataset B 的 GRE 说明、Dataset C 的系统与数据章节、竞赛评测说明中。 | 逐数据集组织有利于保持来源、标签和任务边界清晰；跨年竞赛只能作为实际使用证据，不能被包装为统一对照实验。 |

**写作启示：** 附录不应成为未完成论证的堆放处。CTBench 把 scoring、bootstrap 和失败分析放附录，仍在正文指出对应发现；NetArena 把三种应用细节放附录，正文保留统一抽象和关键对照。主文必须先交代“为何这些补充材料会改变主张的可信度”。

## 3. 逐篇写作策略与图表功能

### 3.1 RCABench：用预研究把 Benchmark 质量问题变成实证主张

- **章节节奏：** §3 Preliminary Study 有显式 RQ1–RQ3：检查旧数据集结构、比较 SimpleRCA 与已有算法、解释简单方法为何有效；§4 讲数据构造；§5 预先声明新数据验证 RQ4–RQ5；§6 逐项报告；§7 讨论效度威胁和后续研究。
- **论证组合：** Table 2 让异常现象可量化；Fig. 2 的 Eadro CPU 案例让“根因服务显著信号”可视化；§4.7 SLI 门禁把“有效样本”变成可执行质量规则；§6 用 9,152 次注入筛至 1,430 个案例、再用 11 个算法做基准测试。
- **图表职责：** Fig. 1 总览工作流；Table 1 审计旧数据集字段；Table 2 提供 SimpleRCA 反例证据；Figs. 3–7 说明工作负载、标签、收集和有效注入；Figs. 8–9 对比新基准覆盖与复杂性；Figs. 10–11 解释失败类型；Figs. 12–13 支撑可扩展性分析。（本地 PDF pp. 4–17；§3–6）
- **值得借鉴：** 不把“低分”本身当贡献，而解释低分由故障信号、传播距离或观测缺失等设计决定。它也展示强基线可以用来审计 benchmark shortcut。
- **需谨慎：** 数据构造、样本筛选和算法结果都来自同一测试床；Top@K 仅服务级根因，不评 Agent 过程；SLI 筛选可能改变样本代表性。需把“更难”与“更真实”分开论证。

### 3.2 NIKA：先定义运行接口，再证明可用性和诊断成本

- **章节节奏：** §2 Background & Motivation 后，§3 分成 framework overview、benchmark creation methodology、orchestrator；§4 再报告 setup 和 performance；§5 讨论教育/扩展/局限。实验框架在结果之前说明如何运行，避免准确率表缺少任务语义。
- **图表职责：** Fig. 1/2 解释系统组件和 Agent 接口；Fig. 3 用 DataCenterIncast 示例把拓扑、故障、流量、目标和权限串起来；Table 1 汇总 54 种 issue；Table 2 展示 GPT‑5、GPT‑5-mini、GPT‑OSS 在 Detection/Localization/RCA 及成本上的差别；Figs. 4–5 分解类别结果与工具使用；Fig. 6 分析规模变化。（§3–4，Appendix A–B）
- **论证组合：** 150 个 incident、三个模型和重复随机目标提供初始性能切面；成功/失败轨迹案例解释低分机制；规模实验表明 detection 与 root-cause 深度受影响不同。
- **需谨慎：** 无形式 RQ，更多是框架展示加基线研究；实验整体耗时长、样本子集有限，没有充分统计检验；“工具轨迹记录”不等于过程因果评分；仿真注入标签并非生产专家真值。

### 3.3 CTBench：把任务质量控制、过程评分和 Agent 结果分层呈现

- **章节节奏：** §2.2 用 Table 1 对比基准属性；§3 定义 RCA/Path 任务、构造流程和元数据；§4 定义 scoring；§5 先主结果，再按成本、类别、可观测性/异构度、层级相似度剖析；§6 归纳；§7 局限。
- **图表职责：** Figure 1 展示盲审/协商保留流程，Table 1 建立差异定位；Fig. 2 或 §3 任务图解释交互接口；Table 5 给主性能/证据面板，Table 6 独立展示成本；Fig. 3–4 将准确率分解到故障类别和复杂度；Appendix A 的任务/分布表、B 的额外指标、C 的证据和错误分解、D 的统计设计、E/F 的轨迹失败类型构成复核链。（§3–6、Appendix A–F）
- **论证组合：** 234 个专家案例不是直接作为“高质量”证据；论文说明 359 候选如何筛选，并做 blinded solvability review。Agent 结果证明两种任务的难度和能力差异；O2→O1 消融检验直接证据的影响；配对统计与固定底模 Harness 对照限制解释范围。
- **需谨慎：** 任务来自真实维护材料，但执行使用 CLI 输出回放；golden action recall 偏向专家路线；Pass@1 的跨任务误差不包含同一任务多次运行方差。应把“专家路线 coverage”与“充分因果证据”分开表述。

### 3.4 NetArena：用统一抽象串三类应用，再安排三项针对性实验

- **章节节奏：** §3 先区分 constructive/reactive 任务，再给状态转移、query/GT 生成和 emulator integration；§4 的三项实验分别对齐样本量可靠性、复杂度下的细粒度表现、训练数据难度泛化；§5 讨论 RL/对抗生成和 sim-to-real。
- **图表职责：** Fig. 1 把输入配置、任务生成、状态/动作、执行反馈、安全检查和最终态评价放入一图；Fig. 2 用 Capacity Planning 与 Routing 场景说明任务差异；Table 1 声明既有 Benchmark 比较维度；Fig. 3 把小样本与大样本的正确率/安全率 CI 以及失败例并置；Fig. 4 按复杂度等级分任务展示 correctness/safety/latency；Table 2 给具体失败类型；Fig. 5 支撑 SFT 泛化主张；Fig. 6 是探索性 RL 结果。（§1、§3–5，Appendix B–D）
- **论证组合：** 9,250 动态 query 支撑统计区间变窄；L1–L3 分类支持细粒度能力差异；SFT 对照试图检验训练难度泛化；RL 是较小规模可行性示例，不能与主要 benchmark 对比等量齐观。
- **需谨慎：** SFT 数据规模与难度覆盖混杂；正文 Figure 3 模型排名叙述与图读数有未解差异；查询之间是否独立没有被充分论证；动态生成避免固定题记忆不等于无生成模板偏差。安全和 latency 在三种应用的实现口径不同。

### 3.5 互补三篇：数据、评分与社区使用各自承担不同论证

- **OpenRCA**：Fig. 1 讲数据/框架；Fig. 2–3 讲筛选校准；Table 1 数据特征、Table 2 模型与采样结果、Table 3 多元素难度；Fig. 5 跨系统结果、Fig. 7 案例轨迹；附录补校准、prompt 和案例。它用结果说明“在这套筛选后的企业案例中仍有困难”，没有证据支持“任意生产任务”外推。（§2–6，Appendix A–D）
- **AgenticOpsEval**：Figure 1 先给三支柱和双数据集地图；Figure 2–4 / Tables 2–5 说明标签、证据和指标；Figure 5–6 / Tables 6–9 做经验性数据剖析；§6 讨论不合格注入和限制。写作上它是“标签与评价构念论文”，而不是全面模型排行榜。（§3–6）

## 4. 七篇论文共同显示的写作准则

1. **贡献要在摘要和引言形成闭环。** 每一项“提出了什么”都应能指向具体机制/数据/评价，并由实验结果回答它解决了什么问题。
2. **先证明要解决的问题存在。** 用审计、案例、任务缺口表或专家复核说明旧基准不足，避免只凭作者判断。
3. **把数据构造写成可复核的流程。** 报告来源、筛选分母、拒绝原因、标签形成与版本；说明“注入、影响、观测和根因”不是同一事实。
4. **让图表承担明确论证任务。** 一张图应解释系统/数据机制，一张表应定位覆盖差异，一组结果图应回答实验问题；不要把架构图当成实验有效性证据。
5. **将结果和解释分开。** 先报告数值、分母和不确定性，再解释；把相关性、代理指标和外推边界标出来。
6. **把附录纳入论证链。** 指标公式、任务样例、统计方法、错误案例及模型配置可能改变主张；正文应引用它们，而不是让读者自行猜重要性。
7. **不把使用规模当作方法验证。** 比赛队伍、下载量和数据行数可以证明资源被使用，不能代替标签质量、实验显著性或模型泛化。
