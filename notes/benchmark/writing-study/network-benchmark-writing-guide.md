# Network AIOps Benchmark 论文：写作与实验设计参考

## 1. 使用边界

本文把已读 Benchmark 论文转成我们未来论文的写作决策框架，不是论文草稿，也不是对现有挑战赛数据的评价。本次没有访问原始样本、字典、注入脚本、标签、切分或评估器；此前知识库提到的 inode/process count/fd、时间边界、节点角色绑定、长尾和传播范围只是待核查问题。所有潜在贡献必须在资料盘点和实验后再决定。

参考依据主要来自 [RCABench](../../../papers/benchmark/rcabench/notes.md)、[NIKA](../../../papers/benchmark/nika/notes.md)、[CTBench](../../../papers/benchmark/ctbench/notes.md)、[NetArena](../../../papers/benchmark/netarena/notes.md)、[OpenRCA](../../../papers/benchmark/openrca/notes.md)、[AgenticOpsEval](../../../papers/benchmark/agenticopseval/notes.md) 和 [Constructing Large-Scale](../../../papers/benchmark/constructing-aiops-benchmark/notes.md)。本地资料缺口见[数据集设计启发](../../benchmark/dataset-design-insights.md)及[研究缺口](../../benchmark/research-gaps.md)。

## 2. 先选研究定位，再决定论文结构

不必套用一个固定模板。应根据现有数据实际具备什么，选择以下一种主叙事；多条可组合，但每增加一条就需要相应的独立证据。

| 可选定位 | 核心研究问题（待验证） | 可能贡献 | 何时适用 / 主要风险 |
|---|---|---|---|
| **数据质量与真实故障谱系** | 一个网络 AIOps 数据集怎样证明故障样本、标签、影响和观测证据可靠？ | 对挑战赛数据做系统质量审计；明确有效事件与无影响/不确定事件；构建设备—接口—链路—流量/业务的标签及证据关系；开放可复核协议。 | 适合原始样本、注入记录、标签与筛选历史可取得时。若只有最终导出数据，不能声称已验证因果和构造过程。可借 RCABench 的 SLI 门禁、OpenRCA 的工程师校准及 ZTE 的数据谱系组织。 |
| **网络诊断任务和跨基线评价** | 当前诊断方法是否利用了拓扑/多模态证据，还是依赖容易的节点角色、指标或注入模式？ | 网络特定任务 schema、具有意义的硬负例/Shortcut 对照、层级或多根因评价、按拓扑/故障族泛化结果。 | 适合存在稳定诊断标签和可运行评估器时。若只报告 random split 上总体准确率，容易成为常规数据资源论文。参考 RCABench 对简单基线的审计、OpenRCA 的分字段难度。 |
| **交互式 Network Agent 排障** | Agent 在部分可观测网络中如何选择调查动作、定位根因并提供可验证证据？ | 工具/CLI 接口、可追溯轨迹、专家标注的证据/替代路线、真实 Token/时间/工具成本；对静态数据集无法评价的多轮调查进行测量。 | 只有任务接口、可复现环境和证据数据齐备时采用。CLI 日志回放与动态网络模拟必须分开声明。参考 NIKA 的实时工具交互和 CTBench 的专家轨迹，但要避免 golden route 等同唯一正确过程。 |
| **动态安全操作/恢复** | Agent 能否在权限、业务约束下修复故障、验证服务恢复并在失败时回滚？ | 状态转移、逐动作安全约束、独立 SLI/连通性恢复判定及动作风险指标。 | 需要隔离仿真/测试床、状态快照、操作约束与安全审查。否则不要把诊断数据包装成安全修复 Benchmark。参考 NetArena 的目标态/Safety 分离，并吸收 NIKA 对主动探测副作用的边界。 |
| **统一多赛道 Benchmark** | 离线历史事故、固定回放和动态仿真上的 Agent 能力如何迁移？ | 同一事件谱系支持离线诊断、交互回放和动态模拟的桥接；拆分评估数据源偏差、观测和动作影响。 | 科研价值可能最高，但集成、数据映射和标签成本也最高。应先证明各赛道分别可信，再做跨赛道迁移，不能把规模相加后声称统一真实度。 |

优先用真实资料回答“我们具备哪项独特、可验证能力”，再确定标题和贡献。标题应与主贡献一致：数据资源、诊断 Benchmark、Agent 交互系统和安全恢复不是可互换标签。

## 3. 推荐的论证骨架

下面是按定位可增删的章节职责，不是要求每篇论文都采用同一顺序。

1. **Introduction：** 一段 operational need；一段既有 Benchmark 的具体不足及证据；一句清晰研究问题；逐项列贡献，并在段末说明每项贡献由何种证据支持。
2. **Task and Scope：** 明确定义任务输入、候选空间、输出、允许信息、是否 Agent 可交互、任务终止条件。区分 Anomaly/Failure Detection、Localization、RCA、Diagnosis、Remediation、Recovery Verification。
3. **Data Provenance and Construction：** 描述来源、系统/拓扑、时间范围、数据模态、采样、故障/事件构造、筛选流和每一步分母；单独说明合成/注入/真实事件及其标签生成机制。
4. **Label and Quality Validation：** 根因、症状、影响、传播、时间和证据分别定义；报告专家背景、盲审流程、分歧/一致性、无法判断和拒绝样本。注入日志不能单独充当业务影响真值。
5. **Benchmark Protocol and Metrics：** 固定可见信息、候选空间、数据切分、工具权限、超时与复现方式；解释每个指标分母、近似匹配、多个正确答案和空/不确定答案的处理。
6. **Experiments：** 先数据/质量有效性，再基线与任务难度，再消融/泛化，再成本/Agent 过程；每个实验都对应一项 RQ/贡献，不为“实验多”而加无关表格。
7. **Discussion / Limitations：** 说清外部效度、选择偏差、标签争议、模板泄漏、仿真—生产差异、数据访问/许可和未完成评测。
8. **Appendix：** 放 schema、标注指导、抽样和过滤、模型/工具版本、统计方法、逐任务详细结果、样例任务与错误分类；主文对改变主要结论的附录材料要有明确导读。

## 4. 最小必需实验与可选扩展

| 阶段/实验 | 要回答的问题 | 设计建议 | 结果呈现与停止条件 |
|---|---|---|---|
| **E0：数据谱系与质量盘点** | 数据从哪里来，什么样本被纳入/排除？ | 固定版本；逐项统计原始事件、注入/事故尝试、成功执行、可观测影响、可标注、最终使用的分母；按故障/设备/数据模态列出排除原因。抽样核验时间、实体和标签引用。 | 数据流程图 + 候选/保留/排除表。若无法追溯注入或标签，就把结论限定为发布数据的描述，不宣称“验证因果故障”。 |
| **E1：标签与可解性验证** | 标注是否能从实际提供的证据支持？是否有多解/不确定？ | 专家盲解小样本；一部分双标；报告一致性与仲裁；根因、影响、传播边、时间、证据分别评分；保留“无法判断/多根因”。 | 标签结构图 + 代表事件案例。若参考路线不唯一，建立等价证据类或只评最终诊断。 |
| **E2：任务有效性 / shortcut 审计** | 是否有简单规则、角色或数据痕迹可以绕过目标能力？ | SimpleRCA/多数类/单特征基线；按设备角色、故障类型、时间、拓扑、模板分组；移除/置换可疑特征；负对照和无影响样本。任何可疑特征需由真实数据核验。 | 基线对照表、消融图、数据泄漏风险案例。只在随机切分下好看，不足以支撑泛化主张。 |
| **E3：标准基线** | Benchmark 是否能区分朴素方法、专业算法和学习模型？ | 传统网络异常检测/拓扑 RCA/时序方法；清晰控制输入模态、候选空间、时间窗、训练资源；不把 oracle 特征筛选与部署条件并列成公平冠军。 | 主表报告分任务/分故障族分数、置信区间和分母；简单方法表现强时先解释数据结构，不遮蔽结果。 |
| **E4：泛化与稳健性** | 换拓扑、设备、故障族、流量、版本或时间后是否仍成立？ | 主测试集做 group holdout：incident/fault family/topology/vendor/role/template/time；训练和测试的共同实体/脚本/模板显式统计。动态生成时以 template/family 分组，不默认每个 query 独立。 | 泛化矩阵或跨域性能下降图；将支持范围写成被留出维度，别用单一“large scale”替代。 |
| **E5：Agent 过程（有交互接口时）** | Agent 是否找到证据、以何种成本和风险做到？ | 每次工具调用连到实体、返回观察和后续主张；golden actions 作为参考路线而不是唯一解；单独统计工具、Token、时延、轮次、失败/重复查询；有主动探测时记录网络负荷。 | 主文把答案、证据、成本分面展示；正确但无证据与证据齐但答案错都应可见。 |
| **E6：安全与恢复（可选）** | 动作是否越权、破坏健康路径，是否真的恢复服务？ | 隔离环境；动作前后约束；权限分级；健康路径负控；恢复后 SLI 稳定窗口；回滚和失败动作记录。 | Safety、Correctness、Recovery 分开；若只有模拟器约束，就把安全结论限定为已实现的约束。 |
| **E7：统计与重复性** | 差异是否超出样本及运行随机性？ | 任务配对；bootstrap 或合适的配对检验；按事件/模板 cluster bootstrap；多重比较校正；Agent 如有随机采样则在关键任务多次运行。 | 说明 CI 的随机单位；动态生成数据报告种子、依赖及相关结构。样本多并不自动消除生成器偏差。 |

**不必强制做：** 大量模型榜单、没有研究问题的消融、跨论文无法对齐的最佳成绩总表、未控制的数据规模对照、为获得显著性而重复检验多个阈值。

## 5. 贡献—证据规划表

正式写作前可为每项拟议贡献填一行；证据栏留空时先补研究，不先写成结论。

| 拟议贡献（当前是假设） | 要有的机制/交付物 | 关键证据 | 反证/失败标准 | 目前状态 |
|---|---|---|---|---|
| 网络故障样本包含可检验传播关系 | 事件谱系、拓扑和带来源的传播标签 | 事件级样本 + 专家/时序/遥测证据校验；和仅标签方案对照 | 多数传播边只是从注入目标推断，缺独立证据 | 待原始数据与标注审计 |
| 数据集抑制常见 shortcut | 生成/筛选规则、负对照、分组切分 | 简单单特征基线、角色置换/模板留出、外推分数 | 随机切分高分、换模板后崩溃，或规则基线仍接近顶线 | 待验证；先不要作为创新事实 |
| 多模态证据能提升网络 RCA | 数据对齐和明确的模态访问协议 | 单模态、多模态、缺失模态和时间错位消融；按故障族报告 | 模态贡献由标签或 oracle 先验泄漏造成 | 待实际运行与控制变量 |
| Agent 调查过程可复核 | 统一工具 API/回放或仿真、执行轨迹、证据 schema | 答案—证据—成本分开指标、等价路线、人工评定 | 只记录工具调用但不能证明证据相关，或 golden path 过窄 | 需先确认数据/接口能力 |
| Agent 可安全修复并恢复网络服务 | 隔离状态环境、动作约束、回滚与独立健康检查 | 逐动作违规率、错误副作用、恢复后 SLI、回滚成功率 | 只按最终配置正确性打分，未测健康业务影响 | 当前没有已核验材料，不应声称已有能力 |

用这张表把研究发现和资源清单分开。公共挑战赛历史、数据行数、参赛队伍和开源代码可以增强资源价值，却不会自动填满“机制、对照、反证”三列。

## 7. 结果解释与统计论证

- **报告分母和统计单位。** 事件数、故障注入尝试数、筛选后题数、根因条目数、query 数和遥测行数是不同量。分布图若按标签数统计，不要写成按事件比例。
- **正确性之外，给出基线和失败例。** RCABench 的 SimpleRCA 说明 benchmark 可以被朴素规则审计；CTBench/AgenticOpsEval 的证据标签说明答案正确也可能证据不足；NIKA/NetArena 的运行轨迹说明成本和安全独立存在。
- **把随机单位写清。** 对动态生成题，CI 只在采样独立假设下解释。按同一 template / fault family 生成的查询应考虑 cluster bootstrap 或按组留出。CTBench 单次 Pass@1 的任务间 SE 不是同任务运行误差。
- **实验差异不等于因果。** 两个异构度子集的得分不同，只能说关联；要说异构导致性能下降，需要可控对照或足够控制混杂。NetArena SFT 样本数量和难度混合需分离，否则提升归因不唯一。
- **解释统计显著性，也解释实践意义。** 报 p 值/CI 之外，说明绝对差、分布和每类样本数；无显著差异不等于完全等效。
- **对过程指标限定构念。** Golden-action recall 衡量参考动作覆盖；evidence checkpoint coverage 衡量已标注观察点命中；reasoning trace 长度是文字长度代理。除非验证指标与诊断证据使用相符，不能把它们叫作“真实推理质量”。
- **负结果要作为贡献证据的一部分。** 如果 Agent 在长尾、多个独立故障、部分观测或大拓扑上失败，分析失败是数据集暴露了什么能力界限，而不是只强调平均榜单。

## 8. 开始写作前必须收集的本地材料

1. Challenge 原始数据及授权/许可；版本、文件清单与 checksum。
2. 数据字典：设备/节点/接口/链路、指标/日志/告警、时间戳和缺失值语义。
3. 注入/事故记录：计划、实际执行、参数、故障/恢复时间及数据生成脚本版本。
4. 标签来源：注入 ground truth、工程师报告、拓扑、运维工单或事后校准分别记录；争议与 unknown 保留。
5. 原始 train/dev/test 切分和历届竞赛 scorer；重新评估需固定每个版本。
6. 已发现的候选 shortcut 特征（例如此前讨论的 inode、process count、fd）对应的样本级证据、相关性控制和反事实检查。当前并无可核查的本地原始资料支持这些为实际泄漏。
7. 如果提出 Agent 轨道，收集命令权限、观测返回、执行副作用、真实工具成本和健康检查；否则限定为离线诊断 Benchmark。

## 9. 推荐推进顺序

1. 先建立一张 `claim → required artifact → validation experiment` 表，并为每个潜在贡献写下可能的反证。
2. 盘点数据和版本，再选一小部分样本做根因/影响/时间/证据人工复核；此处决定“数据质量论文”是否站得住。
3. 做最小 baselines 和 shortcut audit；如果简单基线足以接近上限，先解释任务边界并修正评价，而不是立即增加新模型。
4. 按实际能力决定论文主线：离线数据、专家任务、动态 Agent 或恢复安全；不要为了追新把不具备的 Agent 闭环写进贡献。
5. 先完成实验与图表，再写摘要和引言；结果支撑关系清楚后再提出潜在创新。
6. 做一次定向证据核对：版本、表格分母、公式、图文差异、统计单位、数据许可；用风险和结论重要性决定检查深度。

该顺序综合 RCABench 的预研究—构造—验证、CTBench 的盲审—过程指标—错误分析、NetArena 的 query scale/complexity/SFT 分解，以及 ZTE 对不同数据谱系的分别叙述。它是适配当前项目的建议，不是任何一篇论文声称的标准流程。
