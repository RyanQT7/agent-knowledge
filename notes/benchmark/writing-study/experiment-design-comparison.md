# Benchmark 论文的实验设计与贡献—证据映射

## 1. 研究范围

本文件综合七篇论文已经精读的正文、附录与笔记，并对四篇重点论文的主要实验页、关键结果图和统计说明作了定向原文核对。没有重新运行方法、数据构造器或 Agent。定位以论文章节/表图/附录为准；“我们的归纳”表示论文未正式列出该 RQ。

## 2. 逐篇实验设计

### 2.1 RCABench：先审计旧基准，再验证新基准的挑战性

论文明确给出 RQ1–RQ5。前三个问题属于**基准审计/动机实验**，后两个属于**新数据集有效性与算法评测**。（本地 arXiv v2 §3、§5–6；正式版精读定位见 [RCABench 笔记](../../../papers/benchmark/rcabench/notes.md)）

| 实验 | 研究问题、设计与对照 | 主要结果和论文结论 | 支撑贡献及仍未解决的问题 |
|---|---|---|---|
| 旧数据集结构审计（RQ1；§3.1、Table 1、Fig. 1） | 检查四个常用微服务 RCA 数据集的故障类型、注入目标、调用依赖和遥测特征；按最强症状位置分 Type I/II/III。 | 多数样本的注入服务有明显信号，或可观测信息不足，支持“测试集可能允许症状捷径”的动机。 | 支撑论文指出的 benchmark quality gap；分类依赖作者的异常阈值与数据可见性规则，不等于统一外部审计金标准。 |
| SimpleRCA 对照（RQ2–RQ3；§3.2、Table 2、Fig. 2） | 在旧数据集上以指标阈值、Trace 延迟和日志关键词构成简单规则基线；与论文报告的 SOTA 结果比较，并用真实案例检查强信号。 | SimpleRCA 在多个数据集上达到或超过已有方法；如 RE2-OB / RE3-TT 等场景 Top@1 差距明显。Eadro CPU 案例显示注入服务信号突出。 | 这是论文最关键的“反常现象”：高分可能由数据结构而非算法能力造成。旧方法参数/实现来源不同、比较非统一重跑，结论针对已报告结果。 |
| 生成与有效注入验证（RQ4；§4.3–4.8、§6.1、Figs. 3–9） | TrainTicket 动态负载、故障类型/参数、层级标签、多模态遥测；9,152 次注入尝试，经服务 SLI 门禁留 1,430 个案例；比较工作负载/规模/数据特征。 | 84.4% 的尝试未形成可辨业务异常；保留样本在故障族、模态、拓扑和因果复杂度方面覆盖较广。 | 支撑自动构造和 impact-driven filtering。SLI 门禁可能排除被容错吸收或局部影响的灰色故障；数据集仍是单一可控测试床，分组留出不足需继续核对。 |
| 11 种 RCA 方法（RQ5；§5.2–5.3、§6.2、Tables 3–?、Figs. 10–11） | 在新 benchmark 上比较 11 种传统方法，以 Top@K/MRR 和时间评价；按故障类型及难例分析模型表现。 | 平均 Top@1 约 0.21，最佳 MicroRCA 约 0.37，SimpleRCA 约 0.28；网络、DNS、时间偏移等更难。262 个难例的多标签归因为 scalability、observability blind spots、modeling bottlenecks。 | 支撑“新数据触发不同算法短板”，但低分本身不证明更真实。主比较主要使用服务层标签，没有检验完整传播路径、Agent 证据或修复。 |
| 可扩展性测量（§6.2.4、Figs. 12–13） | 对 Trace/Log 方法改变样本量，测运行时间/资源趋势。 | 多数方法随着遥测量增长而变慢，部分达到不适合近实时应用的量级。 | 将“诊断质量”与“是否能在操作窗口内完成”分开；单机资源与测试床规模影响外推。 |

**实验组织特点：** 本文不是把新数据上的 leaderboard 当成唯一结果，而是让“旧基准会奖励简单方法—新基准通过质量门禁构造—传统方法在新集出现不同失效”形成证据链。复核时要保留不同版本的章节/表号差异。

### 2.2 NIKA：系统可运行性、任务难度与操作成本

NIKA 没有显式列正式 RQ。以下 RQ 是根据 §4 的实验归纳，而非论文自称。（§3–5，Table 2、Figs. 3–6、Appendix A–B；[NIKA 笔记](../../../papers/benchmark/nika/notes.md)）

| 归纳问题 / 实验 | 设计与控制 | 主要结果和发现 | 支撑贡献及边界 |
|---|---|---|---|
| Agent 能否完成递进诊断目标？（§4.1–4.2、Table 2、Fig. 4） | 从 640 个基本配置中取 150 incidents；GPT-OSS:20B、GPT-5-mini、GPT-5；任务含 Detection、Localization、RCA；每个模型用随机故障设备/组件实例运行。 | GPT-5 平均检测 89%、定位 68.7%、RCA 55.3%；从检测到 RCA 明显下降。按类别，resource contention 更难。 | 支撑框架能呈现不同诊断层次；150 个样本并非每个任务族都大样本，未报告完整置信区间/显著性。模型和提示/框架也共同影响结果。 |
| Agent 调查路径和工具使用有何差异？（§4.2、Fig. 5） | 比较 GPT-5 和 GPT-5-mini 成功/失败案例的工具分布、工具错误与轨迹。 | GPT-5 更常使用应用层诊断；模型总体工具错误率低（约 0.7%/1.6%）。资源争用失败仍可能止于“链路不稳”等浅因。 | 支撑轨迹观测和接口价值；这是轨迹关联，不是随机化工具消融，不能证明某工具调用造成性能增益。 |
| 拓扑规模会影响什么？（§4.2、Fig. 6） | 四种场景按小/中/大拓扑，平均约 11/27/101 节点；观察准确率、工具和 Token。 | Detection 相对稳定，Localization/RCA 随规模下降；Token 接近翻倍。 | 支撑规模分析及效率指标；规模档也可能包含任务构成/实例差异，难以仅凭此归因为节点数因果效应。 |
| 运行轨迹可复用吗？（§4.1、Appendix B） | 公布约 900 条执行轨迹、工具 schema 和 prompts；Diagnosis Agent 先产分析，Submission Agent 再抽结构化答案。 | 使轨迹、工具调用、成本与结果可以共同检查。 | 支撑基准复现和后续方法比较；框架可记录 SLO/丢包不等于该量均作为主结果使用；无修复安全评估。 |

NIKA 最有价值的图表顺序是：Fig. 3 先让读者看到一次任务如何构成；Table 2 回答“模型能做多少”；Fig. 4–6 再解释类别、工具和规模上的变化。这种“执行示例—主结果—诊断性分解”比孤立放一个准确率表更能支撑 Agent benchmark。

### 2.3 CTBench：专家任务质量与多维 Agent 能力剖析

主实验采用四个固定 Agent–LLM 组合、统一任务集、zero-shot、单次 Pass@1、无重试；单任务上限 3,600 秒。标准误反映任务间差异，不反映同一任务多次生成的随机性。（§5.1、Appendix D；[CTBench 笔记](../../../papers/benchmark/ctbench/notes.md)）

| 实验 | 设计与控制 | 主要发现 | 解释边界 |
|---|---|---|---|
| 任务可解性与人类基线（§3.2、§5、Fig. 1、Appendix A） | 15 名资深电信专家产出/校正 359 候选；盲解时不看答案与路线，复核 solvability、答案、gold actions、metadata；最终留 234 项。另由 5 位专家在不同于任务审稿阶段的设置下作答，每题由一位专家回答。 | 102/126 RCA、104/108 Path 答对；估计每题 40–60 分钟。 | 证明专家参与构造、题目可解并有人工能力参照；不等于对每条真实 RCA 做了多标注者一致性统计，也非与模型严格同人同预算的配对比较。 |
| 主能力和证据覆盖（§5.1、Tables 5、18） | 四组 harness/model 在 126 RCA、108 Path 任务上 pass@1；分开报告 exact、定位/原因/路径 IoU、golden evidence coverage。 | 最强配置也常答对而缺少专家要求证据：Codex+GPT‑5.5 的精确正确子集内 47/60 RCA 和 93/95 Path 未覆盖全部 golden action。 | 直接支撑“最终答案≠证据获取”；golden actions 是参考路线，不覆盖所有等价调查方式，不能据覆盖缺失断言没有因果证据。 |
| 效率和成本（§5.2、Table 6） | 记录 rounds、wall time、实际输入输出 Token，按任务类型分开。 | 高 Token 组合不一定有更高准确率；路径任务资源消耗可能高于 RCA。 | 支撑资源成本要单列；模型 API、上下文、Harness 的差异仍混杂。 |
| 故障类别与难度（§5.3、Fig. 3） | 按五类故障域拆分 RCA 表现。 | Interface/Link 类对所有组合都难；模型在类别上的强弱不一致。 | 说明平均值隐藏类别缺口；长尾任务数有限时需同时显示分母。 |
| 部分可观测消融（§5.4、Tables 20–21） | 对 19 个 O2 RCA 任务加入直接证据形成 O2→O1 对照。 | 多数组合增加直接证据后准确率改善；部分模型提升幅度大。 | 是同类任务的信息条件干预，但证据参考路线长度也改变（平均 4.32→2.95），所以 evidence coverage 不可直接用不同分母比较。 |
| 网络异构性（§5.4、Table 22） | 比较低/高异构任务子集。 | RCA 准确率在高异构子集通常下降；路径任务变化混合。 | 两组是不同任务子集，作者也说明是相关性而非严格因果效果。 |
| 结构相似度与固定模型 Harness（§5.5、Appendix B.1–B.3、C.5、D.2） | Triplet/sequence IoU、根因类型层级和拓扑节点相似度拆分错误；另固定 DeepSeek 模型比较 harness，配对检验并进行校正。 | 层级/拓扑相似得分能显示“接近正确”与精确命中差异；固定底模下若干准确率差异未达到校正后显著性。 | 不能从一项 Harness 排名推断其普遍优越；结果可能来自工具调度、状态处理、停止和答案提取整体组合。 |
| 轨迹失败分析（Appendix E–F） | 对 Codex+GPT‑5.5 的 RCA 错误轨迹做事后分类，分析证据覆盖、因果最小化、对象归属及结构化输出等。 | 将错误从“模型错了”细分成 Agent 能力弱点和任务压力。 | 单一配置的 post-hoc taxonomy 用于机制解释，不是总体错误率的因果分解。 |

**写作特点：** CTBench 把构造质量实验、模型能力实验、指标附录和错误轨迹分层，而不是用一个总分覆盖全部主张。Table 5 与 Table 6 分开是重要选择；Figure 1 应在读者看到模型结果前说明任务筛选可信度。

### 2.4 NetArena：三项主实验分别检验动态 Benchmark 的不同价值

NetArena 的实验布局直接对应 §1 的几项主张，不把一个结果包揽所有价值。（§4.1–4.3、§5.1、Figs. 3–6、Tables 1–2；[NetArena 笔记](../../../papers/benchmark/netarena/notes.md)）

| 实验 | 研究问题 / 设计 | 结果及支撑主张 | 实验不足 |
|---|---|---|---|
| Query 数量与 CI（§4.1、Fig. 3） | 小集合 CP:100、Routing:150、K8s:150，对比大集合 CP:5,000、Routing:2,250、K8s:2,000；对二元成功率用 Bernoulli SEM 构造 95% CI。 | 小样本模型区间大量重叠，扩大到 9,250 queries 后重叠比例降至 0；支撑大样本提高比较分辨率。 | 置信区间缩窄依赖 query 独立/抽样假设；CI 不重叠不是配对显著性检验，也不能证明生成样本对生产故障的覆盖。 |
| 复杂度分解与失败案例（§4.2、Fig. 4、Table 2） | 按每个应用的 L1–L3 难度分析 correctness、safety、latency，并分类安全、控制逻辑和操作错误。 | 不同 Agent 在任务/指标上强弱不同；聚合正确率会隐藏复杂度下安全下降、过度保守或多余动作。 | 应用任务和安全实现不同，跨应用 radar 图不是一个完全同构任务的受控比较。 |
| SFT 难度泛化（§4.3、Fig. 5） | CP 任务用不同难度数据训练后，测试各难度等级及 safety；训练样本量、难度覆盖、混合比例共同变化。 | 单一难度训练出现域内强、跨难度弱；混合难度表现总体较好但各级并非正文概述一致。 | 样本数和难度混杂；正文与 Figure 5 对 Level 2 Correctness/跨级 Safety 的描述存在冲突，不能用不一致图文得出强结论。 |
| RL 可行性试验（§5.1、Fig. 6） | Qwen2.5‑0.5B 在 Mininet routing 上使用 GRPO 和人工设置的无效命令/诊断/修复 reward。 | 约第 36 episode 后累计奖励上升，展示该环境可作为训练接口的初步例子。 | 单模型、单环境、小试验，不证明稳定学习、泛化或比监督/其他 reward 更好；对抗任务主要是展望。 |

**图表观察：** Fig. 3 将 correctness 与 safety 画成二维点图，读者能看到“答对但不安全”和“安全但没修好”的权衡；Fig. 4 用 L1–L3 小图显示任务难度行为；Table 2 让抽象失分变成可理解的具体错误。这三种图互相补充，不能替代生成器独立性检查和正式统计检验。

### 2.5 OpenRCA、AgenticOpsEval、Constructing Large-Scale 的互补实验

| 论文 | 实际实验/经验分析 | 结果证明什么 | 不应据此声称什么 |
|---|---|---|---|
| OpenRCA（§4–6、Tables 2–4、Figs. 5–7、Appendix C–D） | Balanced/Oracle sampling、六个 LLM、RCA-Agent 与不同提示/采样对比；按 Telecom/Bank/Market、多字段任务难度分析；案例分析 CoT 和多轮数据调查、Executor 错误处理。 | 经筛选的历史企业故障任务对当前模型很难；字段数量/系统规模改变难度；给定数据工具的 Agent 可能获得新证据。 | Oracle sampling 不是部署条件；更长 CoT 不等于新证据；性能不能无条件外推到开放世界 RCA；错误恢复结果是观察性子集。 |
| AgenticOpsEval（§4.5、§5.5、§6） | 主要是数据/标签统计、故障和证据分布、跨系统描述、注入后专家筛选及比赛使用情况；没有完整、统一的多模型性能比较实验。 | 展示两套数据怎样支持不同粒度的 evidence/causal-chain 评价以及竞赛使用。 | 6,093 支队伍是两项赛事合计使用规模，不是独立 Benchmark 有效性检验；不能虚构论文未报告的模型排行榜。 |
| Constructing Large-Scale（§3–6、Tables 1–8） | KPI 数据的统计/与公开集对照和 2018 竞赛结果；多维数据合成方式、拒绝规则和 2019 竞赛；Dataset C 注入/遥测及 2020 竞赛评测。 | 证明三类任务数据可形成长期公开资源、可按各自任务运行竞赛，并展示各自的标签/指标设计。 | 跨年任务/指标不统一，不是同一模型在三套数据上的受控对比；参加队伍和最佳分数不能替代标签可靠性或统计显著性。 |

## 4. 核心贡献—验证实验—结论边界

| 论文主张 | 最能支撑的实验/材料 | 可以得出的结论 | 不能直接推出 |
|---|---|---|---|
| 旧微服务 RCA 基准可能奖励简单捷径（RCABench） | 旧数据集结构审计 + SimpleRCA 对比 + 具体案例 | 在被检查的四个数据集中，简单特征规则可达到/超过部分已有方法，提示分数依赖任务结构。 | 所有 RCA 基准都无效；或者新 benchmark 更接近全部生产故障。 |
| Network Agent 需要交互环境和工具轨迹（NIKA） | 150 个事件任务结果、轨迹/工具分析、规模分组 | 这三类模型在给定仿真与任务集上表现和成本不同，复杂诊断明显难于检测。 | 生产部署可靠性，或某项工具/Agent 架构导致性能提升。 |
| 电信 Agent 正确答案不能代表证据充分（CTBench） | 正确答案子集中的 golden-action 缺失、O2→O1、盲审流程 | 在专家定义的任务与路线下，答案准确和参考证据覆盖是分离能力；部分可观测/异构子组表现有差异。 | 未命中专家路线就没有有效证据；异构性对所有任务均因果性降低性能。 |
| 动态任务可提高统计区分力并暴露安全权衡（NetArena） | 小/大 query CI、complexity 图、动作错误分类 | 给定生成器和采样设置，样本数提高能缩窄二项率的估计误差； correctness 与 safety 应分开看。 | query 彼此独立、对生产分布泛化，或仿真 Safety 等于真实运维安全。 |
| 历史企业案例和工具 Agent 能形成可测试 RCA 任务（OpenRCA） | 335 案例筛选、Balanced/Oracle/RCA-Agent 对照、多系统和难度结果 | 在特定筛选、候选/窗口和遥测条件下，当前 LLM 多字段诊断能力有限。 | 模型无法处理任意生产日志；采样/Agent 变化单独导致因果提升。 |
| 证据与因果链可进入数据标签（AgenticOpsEval） | 专家校正 key observations 与 RCA100 checkpoints、指标示例 | 可把答案之外的观测依据编码为可计算标签，并服务不同粒度的评价。 | 该评分已证明识别真正因果推理，或论文已完成多模型比较。 |
| 多种 AIOps 数据谱系可支撑不同任务和社区实践（Constructing Large-Scale） | 三数据构造/指标描述、竞赛记录、公开复用 | 不同任务可以由不同数据和协议支持；公开使用提供资源可用性证据。 | 跨三届比赛成绩可直接横比，或竞赛规模证明标注/泛化质量。 |

## 5. 什么实验真正验证 Benchmark 的价值

1. **质量有效性**：注入/候选样本是否产生真实可观测影响；缺失或矛盾数据如何处理；独立专家能否盲解；标签的来源和分歧是否记录。
2. **区分性与难度结构**：简单基线是否能靠 shortcut 得分；问题是否存在可解释的难度梯度；不同标签/证据粒度会否改变结果。
3. **可靠比较**：同任务配对、固定模型/预算、置信区间或配对检验、重复运行方差；动态样本的独立单位究竟是 query、模板还是 incident。
4. **外推/稳健性**：按事件、故障家族、拓扑、模板、设备角色/厂商或时间批次分组留出；在另一个环境或版本复核。
5. **过程有效性（Agent Benchmark）**：跟踪真实工具动作和状态；允许等价证据路线；分别评价答案、证据、成本、安全与恢复，不以文字长度代替真实调用。
6. **外部可用性**：公开 schema、数据版本、评分器和运行协议；竞赛、社区采用是补充证据，不替代前五项。

推荐写作时先为每条贡献列出“必须出现的实验”，并给出一个可能使主张失败的负结果。若数据无法支持某类验证，应缩小贡献表述，而不是补充更强的宣传语。面向本地工作的阶段性方案见[Network Benchmark 写作指南](network-benchmark-writing-guide.md)。
