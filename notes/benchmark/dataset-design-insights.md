# 六篇 Benchmark 对本地 AIOps 数据集建设的启发

## 证据边界：本地数据还不能作事实比较

当前知识库没有找到挑战赛原始样本、数据字典、注入/采集脚本、标签协议、划分文件或 evaluator 版本。因此无法核实数据规模、`inode` / `process count` / `fd` 的生成机制、故障起止时间、节点角色绑定、长尾分布、多模态关系或已公开程度。下面把用户提出的现象当作**待检查假设**，不描述成本地数据已确认缺陷，也不虚构实验结果。

要回答“我们的数据集和论文有什么不同”，第一步应将自有数据整理成相同字段清单：来源与许可、系统/拓扑、事件数量和独立故障数、时间范围/采样粒度、模态、故障类别/根因数、标签证据、拆分方式、基线、评分代码、公开工件及版本。

| 本地关注点 | 论文中的直接参考 | 可以借鉴什么 | 不能据此声称什么 |

## 4. 怎样检验 Shortcut，而不是猜测

先形成数据谱系和威胁模型，然后做简单、可解释的反证实验：

1. **独立单位核查：** 把原始故障事件、时间窗、滑动窗口和增强样本分层计数。切分按事件/注入 recipe 分组，防止一个 episode 的相邻窗口进入 train 与 test。
2. **分组外推：** 至少设置随机切分（作为参考）、跨节点/角色、跨故障模板、跨拓扑/时间切分。注明每种设置的测试事件数和缺失类别。
3. **廉价 Shortcut 基线：** 单字段、时间戳、文件名/序号、主机角色、静态阈值、浅层规则分别预测标签；若简单规则很强，再追查关联是否源于真实机制。
4. **候选特征审计：** 对 inode/process count/fd，确认单位、采集来源、正常行为范围、是否由故障脚本直接产生、是否跨节点共享。使用 feature ablation、组内置换和时间错位；变化只说明模型依赖该信号，不自动证明信号无效。
5. **负对照和反事实：** 打乱标签、错配非根因窗口/拓扑、替换实体 ID；保留业务机制不变时，判断指标是否异常下降或仍异常偏高。
6. **报告范围：** 公布样本筛除原因、生成器/版本、分组键和所有切分结果；不要只展示最有利随机 split。

这些是建议执行的审计方案；本轮未运行任何本地数据检查。

## 5. 怎样构建有说服力的 Ground Truth

建议对每个 event 建立互相区分的字段，而不是一列“failure time / root cause”承载所有含义：

- `injection_or_trigger`：计划故障和实际注入命令/变更；真实事件则记录来源工单/变更。
- `root_cause_candidates`：根因实体、故障机制、证据、标注者及确定状态；允许多根因、Unknown 和 contested。
- `timeline`：触发/注入、最早遥测异常、告警、业务影响开始/结束、缓解操作、指标恢复等分别记时，并保留误差区间。
- `propagation`：有证据的传播节点/链路、顺序、未观测区段；不要仅凭拓扑连接补边。
- `symptoms_and_impact`：指标、日志、trace/网络流、受影响用户/服务和 SLO 改变。
- `evidence_provenance`：来源文件/表、时间范围、定位器、版本、标签来源（脚本、专家、变更、恢复验证）及复核状态。

可用人工 adjudication 保留争议记录；当不同标签定义导致多个正确答案时，需明确任务到底评 root cause、可操作对象还是 nearest affected component。若是注入任务，最好把“脚本目标”“实际命中”“观测异常”“业务影响”作为不同状态，避免把 injection target 直接当真因。

## 6. 怎样体现网络故障传播和拓扑依赖

为事件快照绑定拓扑版本及有效时间。传播标签应能指向设备、接口、链路、路由/协议对象、服务流与中间状态；标出哪些边有遥测或专家证据、哪些只是推断。单独评测根因定位、影响范围、传播链、业务路径和恢复状态。

网络数据可记录源宿、方向、多路径、接口状态、路由决策及业务探针。设置拓扑扰动和跨拓扑 held-out；例如训练集和测试集不共享同一设备 ID 或注入模板。除纯答案外，Agent 可以提交其证据链，但应允许不同合法命令获取等价观察，分别评证据覆盖、结论和工具成本。若动作会改变网络状态，则需要独立沙箱、变更安全及回滚测试，本任务没有触碰这些运行环境。

## 7. 怎样公平比较传统 AD/RCA、LLM 与 Agent

可以共享同一事件版本、标签和时间窗，但需分开协议和结果：

| 方法 | 主要回答 | 最少应报告 |
| --- | --- | --- |
| 传统 anomaly detection | 是否异常、何时开始/结束 | event precision/recall/F1、误报、检测延迟、事件级切分 |
| 传统 RCA/定位 | 哪个实体/指标/路径是根因 | Top‑k / entity-set IoU / 多根因完整性、宏/微指标、运行时间 |
| 单次 LLM | 结构化结论是否正确且有证据 | schema、字段 exact match、证据定位/支持度、拒答、Token/时延 |
| Tool-using Agent | 是否通过调查得到可靠结论 | 上述答案质量 + 真实 tool/API 调用、成功率、调查冗余、证据充分度、Token/费用/时延、权限/状态影响 |

同一 Agent 比较时固定可见信息、工具接口、模型/harness 版本、重复次数和预算；最终答案、证据、工具消耗和安全不能压成一个无法解释的总分。CTBench 的固定 route coverage、AgenticOpsEval 的 trace-length efficiency、NIKA 的真实工具/网络成本各有不同分母，不能直接排名。

## 8. 数据集论文如何组织实验与论证

先讲问题与数据谱系，再给环境/拓扑/模态/时间粒度；随后写事件生成、采集、筛选和标签流程，明确原始数、有效数、排除原因。之后定义任务和开放/闭集假设、标准化答案、切分文件、指标实现及版本。实验应包含：多个传统基线、朴素 Shortcut 基线、跨实体/模板/拓扑切分、模态消融、错误分析、长尾/多根因分层、Agent evidence/cost 分析。最后说明许可、可获得工件、复现实验成本和局限。

设计灵感可映射到这些论文：RCABench 的 SLI 门禁；OpenRCA 的工程师校准与字段组合任务；ZTE Dataset B 的混淆组合筛选；AgenticOpsEval 的分层 evidence 代价；CTBench 的盲解/任务可解性审查；NIKA 的可复现网络工具接口。应选择适合数据来源的部分，而不是完整照抄任一协议。

## 9–10. 可能的研究价值与待验证创新

若现有数据确有跨模态网络故障、可追溯时间边界和可量化传播路径，可能形成以下候选贡献：

1. 将多模态网络观测、拓扑依赖和根因传播标注在同一事件谱系中；
2. 对故障注入痕迹和节点角色 Shortcut 作实证审计，而非只报告随机切分；
3. 对异常检测、传统 RCA、单次 LLM 与工具 Agent 建立分层但共享真值的评价协议；
4. 公开带版本的数据字典、标签记录、切分与 scorer，支持重放。

这些创新目前均是**待数据核验的假设**。下一步最有价值的是补充数据版本、样本字典、拓扑、生成/注入代码、标签来源、切分脚本、基线和公开许可；核验后再判断哪些点有区别度和实验支撑。此处不修改比赛数据、标签或评估器。

## 可检验的最小设计对照

按事件保留入口影响、根因处直接观测、受影响路径和专家可追溯性四项字段，分别统计每道门禁剔除的样本，再在同一批事件上按传播距离和观测缺失分层估计难度。若提供额外证据，保持任务和答案不变并记录参考证据分母的变化。对工具型诊断再固定模型比较 Harness，记录空结果、错误与恢复、真实工具量和资源消耗。撰文时由数据来源、互斥任务、纳入/排除原因、评分合约和独立对照组织论证。这些都是后续待验证设计，当前还没有本地挑战赛样本和脚本支撑。
