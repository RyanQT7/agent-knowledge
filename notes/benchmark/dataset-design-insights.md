# 对本地 AIOps 挑战赛数据集建设的启发

## 证据边界

当前仓库未找到我们所指挑战赛数据的原始样本、数据字典、注入脚本、标签规范或按事件的实验结果。本节依据六篇论文和用户列出的风险形成设计检查项；不能将 `inode`、`process count`、`fd`、节点角色绑定、长尾、故障边界等表述写成已核验的数据集缺陷。有关现有数据集规模、标签和实验表现均标记为**待补充**。

## 1. 我们的数据集与现有 Benchmark 有何区别？

目前无法作事实性对照：数据环境、故障数、采样周期、模态、标签构造、公开状态、基线协议和版本均缺少本地证据。六篇工作覆盖了互补范围：RCABench 强调传播与 SLI 有效性；NIKA 强调可交互网络仿真；OpenRCA 强调大体量企业多模态遥测；ZTE 论文分开 KPI 检测、结构化定位与注入诊断；AgenticOpsEval 标注证据与传播链；CTBench 标注部分可观测条件和专家动作路线。要说明我们的差异，需先用相同字段形成数据集清单。

## 2–3. 值得借鉴的方法与相关局限

| 目标 | 可借鉴设计 | 关联局限 / 使用条件 |
| --- | --- | --- |
| 排除无效故障注入 | RCABench 将注入尝试与最终有效案例分开，检查用户侧 SLI 是否受到可辨影响 | 注入脚本成功不代表业务故障成立；保留失败尝试有助于解释筛选偏差 |
| 多模态及因果标签 | OpenRCA 关联 metrics/logs/traces 和根因元素；AgenticOpsEval 标注证据点和传播链 | 单根因标签不总能概括多根因、并发和不确定案例；需记录标签来源和争议 |
| 生产 / 合成互补 | ZTE 论文将生产 KPI、受控合成定位与故障演练分为不同数据集 | 合成数据可控但构造机制可能变成 shortcut；“真实系统采集”也不自动等同生产故障真实度 |
| Agent 过程 | NIKA 留存调用和状态，CTBench 记录专家动作，AgenticOpsEval 记录 evidence checkpoints | 工具轨迹或 reference-route 覆盖不等于 Agent 理解因果；允许等价合法调查路线 |
| 标注质量 | OpenRCA 的工程师校准、AgenticOpsEval 的独立复核、CTBench 的盲解和争议剔除 | 专家参与不自动证明一致性；应公布分歧、改标和不确定标签统计 |

## 4. 如何减少 shortcut 而不是学故障机制？

建议把 Shortcut 检查写成数据发布协议，而不是只报告一个随机切分分数：

- 按注入模板、故障类型、节点/服务、时间段、拓扑/设备和 workload 分组切分；另给跨拓扑或跨设备外推集。
- 执行 feature ablation、置换/时间错位、负对照和标签预测审计。对候选可疑特征（例如 inode、process count、fd），核对它是否由故障机制产生、是否跨正常/故障条件稳定、是否仅标识节点角色；不能仅因相关系数高就删特征。
- 检查故障类别与节点角色、故障脚本参数、文件路径、采样边界、告警文本是否绑定；报告简单规则/单变量/时间戳基线作为 shortcut 参照。
- 将数据处理与切分在事件级冻结，避免滑窗重叠、同一故障多切片跨 train/test、归一化统计量跨测试集泄漏。
- 对长尾类别报告每类样本数、macro 指标、置信区间和合并规则；不要靠过采样制造测试集重复模式。

以上是建议的检验，不是本地数据已通过或未通过的审计结论。

## 5. 如何建立更有说服力的 Ground Truth？

将单一“根因标签”拆为可追溯的标签层：故障触发/注入点、最早受影响实体、传播中间节点、可见症状、业务影响、事件起止区间，以及可能的多个根因/未知标签。每项记录证据来源（脚本、变更单、专家、遥测、恢复验证）、标注者与复核状态。

对时间边界可保存区间和不确定性：注入时间、首个遥测变化、告警触发、影响开始、恢复操作、指标恢复分别表达；明确最终评估用哪种时间定义。对标签不一致保留 adjudication 过程，不静默覆盖。若是真实事件，区分事后 RCA 结论、时间邻近相关性和有干预/恢复证据的因果判断。

## 6. 如何体现故障传播与拓扑依赖？

每个事件关联版本化拓扑快照，并标注节点/链路角色、传播边、观测到的因果顺序及未观测环节。评测应区分 root-cause localization、影响范围、传播路径、业务影响和单个高相关症状。对网络故障报告 hop 数/受影响路径、源宿/服务流和多路径；支持多根因与共享下游症状。利用删边/改路、局部故障复现等对照验证模型是否依赖拓扑，而非记忆实体 ID。

## 7. 如何共同评价传统算法、LLM 与 Agent？

共用版本固定、相同事件切分、相同根因/范围标签和可重复 evaluator；按任务能力分别报告：

1. **传统检测/定位**：事件级 Precision/Recall/F1、false alarm rate、检测延迟、定位 Top-k、路径/范围指标。
2. **LLM 一次性诊断**：结构化字段精确率、校准/拒答、证据引用正确率及上下文/推理资源。
3. **工具型 Agent**：最终答案质量、证据充分度、调查覆盖/冗余、真实工具调用数、Token、时延、费用与服务影响分别计量；安全动作在沙箱中单独评估，绝不把建议安全性等同已修复。

避免将 CTBench 的单一路径 coverage、AgenticOpsEval 的 reasoning length 与 NIKA 的工具调用量直接做同一数值排名。相同预算下比较时同时公布预算口径和模型/工具版本。

## 8. 数据集论文的实验与论证组织

建议按“数据谱系与许可 → 系统/拓扑/时间覆盖 → 故障/异常生成与筛选 → Ground Truth 和不确定性 → 数据质量/泄漏审查 → 任务定义/切分 → 基线与评估脚本 → 消融和稳健性 → 可复现工件”组织。报告所有收集样本、剔除原因与每步数量；区分生产观测、受控演练和模拟合成；公开数据字段、脚本版本、标签版本、评估器 commit 与限制。

## 9–10. 潜在研究价值与需验证创新

若证据支持，潜在价值可以来自：拓扑/多模态对齐的真实网络事件、可追踪的故障起止与传播真值、对 shortcut 的实证审计、长尾和跨节点泛化、多种算法与 Agent 在一致协议下的比较、可复现的事件和评分脚本。但目前这些是**候选论证方向**，不是已验证创新点。

下一步需先补充：数据集版本/规模和字段字典、数据来源与使用许可、注入或真实事件流程、节点/拓扑关系、故障时间定义、inode/process/fd 特征的数据生成机制、角色/类别统计、train/test 切分、现有 AD/RCA 基线、Agent 工具和真实成本，以及已公开内容。获得这些证据后再判断哪些论文设计直接适用，哪些创新能够成立。
