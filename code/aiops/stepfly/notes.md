## 1. What the Repository Implements

StepFly automates troubleshooting-guide execution. A Scheduler coordinates a
troubleshooting-guide PlanDAG, while Executor agents perform individual graph
steps with an LLM action/observation loop and tools/plugins. The repository
also contains a MongoDB-backed session memory and terminal/web interfaces.

## 2. Repository Architecture

```text
incident ID
  → incident_tsg_loader
  → TSG document + PlanDAG + plugins
  → Scheduler follows PlanDAG / conditional edges
  → Executor runs each step with action tools
  → observation and step result
  → edge/node status update
  → next eligible step or finish
```

## 3. Entry Points

- `stepfly/agents/scheduler.py:Scheduler.start_session` and `_react_loop`.
- `stepfly/agents/executor.py:Executor.execute_step` and `_execute_action`.
- `stepfly/tools/incident_tsg_loader.py:IncidentTSGLoader.execute`.
- `stepfly/tools/schedule_tool.py` monitors PlanDAG node/edge status and starts executors.
- `stepfly/utils/memory.py:Memory` is the shared persistence backend.
- `TSGs/PlanDAGs/*.json` define graph structure and conditional transitions.

## 4. Main Execution Flow

The Scheduler initializes a session, loads tools, and asks an LLM for JSON
`thought`, `action`, and `parameters` in a bounded loop (`scheduler.py:85-156`).
The incident loader maps an incident to a TSG and PlanDAG. The scheduler
launches eligible graph steps; each Executor creates step-local conversation
history and repeatedly calls an action tool until `finish_step`, retry limit,
or failure. Results update node and edge status in the scheduling layer.

## 8. Data Flow

```text
incident metadata
  → TSG/PlanDAG content in Memory
  → scheduler context
  → action/tool parameters
  → tool output observation
  → executor step result
  → graph edge/node status
  → next scheduled executor
```

The memory backend stores data type, timestamp, agent ID, description, and
metadata for many entries. The code does not by itself guarantee that each
stored item is useful, fresh, or correctly selected for later diagnosis.

## 9. LLM Usage

The Scheduler and Executors use an LLM to emit structured next actions and
interpret tool results. This is a genuine bounded tool loop. The graph
scheduler, tool registry, retries, and stop conditions are deterministic
control around the LLM.

## 10. Prompt Design

Scheduler prompts list `finish` and loaded tools; Executor prompts include the
current step and context. The expected action format is JSON. `log_reasoning_tool`
can record a reasoning/observation without executing a diagnostic operation.

## 11. Tool System

Tools include incident/TSG loading, scheduling, SQL querying, code
interpretation, user interaction, logging, and plugins. The inspected code
shows exact dispatch and error strings, but tool results are mostly text and
are not a universal evidence/provenance schema.

## 12. Planning / Orchestration

Planning is explicit at the PlanDAG level: the guide defines nodes and
conditional edges, and `schedule_tool.py` chooses eligible nodes. The LLM
does not freely synthesize an arbitrary global plan in the inspected path;
its action selection is constrained by the current scheduler/executor step.

## 13. Memory / Context

`Memory` uses a MongoDB database named from the session and collections for
agents, generic data, dataframes, and code snippets (`memory.py:14-44`). It
stores conversation/context and data references, and can summarize large
strings. This is operational persistent session state shared across agents,
but the inspected code does not establish cross-session long-term incident
learning, principled memory selection, or forgetting policy.

## 14. Retrieval / RAG

The loader retrieves configured incident/TSG files and memory entries. This is
operational knowledge/context loading, not necessarily RAG. No vector
retrieval lifecycle was required for the core workflow.

## 15. Graph / Topology / Algorithms

The PlanDAG is a troubleshooting workflow graph with statuses/conditions. It
is not automatically a service or physical network topology. It can organize
diagnostic actions, but graph edges do not by themselves prove causal
relations among network entities.

## 16. Verification

Step completion, result status, edge updates, retries, and timeouts provide
workflow control. The inspected code does not show an independent diagnosis
verifier, fresh recovery signal, rollback protocol, or mandatory human approval
before every action. A plugin result is not automatically a verified RCA.

## 17. Evaluation

The repository provides demo/UI/trace paths and synthetic troubleshooting
data. Token, latency, and step traces may be available through common utilities,
but a complete task-success/safety/recovery evaluation was not reconstructed
from static reading.

## 18. Configuration

`config/config.json`, MongoDB settings, TSG/PlanDAG files, plugins, and UI
entrypoints configure the system. Setup requires dependencies and MongoDB;
none were installed or started.

## 19. Deterministic vs LLM Components

- Deterministic: PlanDAG edges, node eligibility, tool registration/dispatch, retries, timeouts, status transitions, memory persistence, and trace logging.
- LLM: scheduler/executor thought/action selection and interpretation of tool output.
- Potential side effects: plugin/code-interpreter tools, if enabled and executed; no code was run in this reading.

## 20. Paper vs Code Differences

The project is described as agentic, and the code does contain scheduler and
executor loops. But the global troubleshooting plan is supplied as a fixed
PlanDAG; “planning” should therefore be reported as graph-constrained
orchestration plus local action selection, not unconstrained runtime planning.

## 21. Reproducibility

Reproducibility is **Medium** for architecture inspection and **Low-Medium**
for execution without MongoDB, configuration, plugins, model/API access, and
demo data. No execution was attempted.

## 22. What I Learned from the Code

StepFly is a useful concrete decomposition of Agentic AIOps: a deterministic
workflow graph supplies operational structure, while LLM loops handle local
interpretation and tool choice. For Network AIOps, this suggests separating
diagnostic policy/constraints from flexible evidence interpretation and
retaining independent verification around any state-changing tool.

## 23. Open Questions

- How are PlanDAG transitions authored and updated when a new incident type appears?
- Which plugin actions are read-only versus state-changing, and where is approval enforced?
- Does MongoDB memory persist across sessions in deployment, and how are stale entries selected or removed?
